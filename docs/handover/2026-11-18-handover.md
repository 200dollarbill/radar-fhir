## 3. Methods

### 3.1 Acquisition (firmware, `arduino/radar_json/`)

- K-LC7 24 GHz radar module, I and Q on AtomS3R pins G7 and G8 (owner's pins; **which is I
  and which is Q is assumed**). 12-bit ADC at 3.3 V (`analogRead`), one read per sample.
- 100 samples per second from a hardware timer in its own task; `sample_idx` is the time
  slot, so lost time shows as a gap, never a burst. IMU accel and gyro in every sample.
- One JSON line per sample over USB serial at 115200. Host to board: `BOARD?`. Board to
  host: `BOARD {"id","key","fw"}`. Logic in `board.h`, host-tested.
- **Board ID**: the ESP32 factory MAC, 12 upper-case hex digits (here `CCBA97030AD4`).
  **Key**: 32 random bytes made on first boot, kept in NVS namespace `prata`; survives
  reflashing the sketch, not a full flash erase.

### 3.2 Data model and interoperability (`fhir_server/`)

- FHIR R4, SATUSEHAT-compatible locally (profiles, identifier systems, terminology), never
  calls the national platform. Resources: Patient, Practitioner, Organization, Location,
  Encounter, Device, Observation. Errors as OperationOutcome.
- Raw signal: one Observation per chunk of up to 1000 samples (10 s), eight components
  (I, Q, accel x/y/z, gyro x/y/z) as SampledData, values as received (V, g, deg/s), `E`
  for a missing sample. Local code system `urn:prata:radar-signal` because no standard
  code for radar I/Q was found (a thesis limitation). Retries use conditional create, so a
  chunk is never stored twice.
- Visit = Encounter, created arrived then moved to in-progress, finished when the session
  ends. Board = Device with identifier system `urn:prata:board`, serial number = board ID.
- Tables beyond FHIR: `boards` (key SHA-256 only) and `board_sessions` (one open session
  per board, unique index).

### 3.3 Sessions, roles, security

- Roles: admin (register boards, create test patients, open and end any session, choose
  the doctor), doctor (open sessions only for patients they already take part in, end their
  own), patient (FHIR API, own records), device (write Observations only into its open
  session).
- The board key is the bearer token for uploads; the server maps it to the board's open
  session at each request. Ending the session ends the write access.
- Login (JWT, 1 h) is kept in `localStorage` so the Sessions and Capture tabs share it.
- **Known weakness (owner's choice, for later):** the board sends its key to anyone who asks
  over the port; the simulated board's key is in `localStorage`. Planned fix: challenge and
  response (HMAC of a server nonce), key revealed once at registration after a button press.

### 3.4 Display processing (the evaluated method)

Display only, not a measurement and not a thesis contribution (the RADAR group owns signal
processing). Code `receiver/src/dsp/`, evaluation `receiver/eval/`.

- **Candidates:** single channel; linear projection (`pca`); arctangent around the mean;
  arctangent around a fitted circle (Kasa fit); extended DACM; `hybrid` (arctangent on the
  fitted circle only if radial spread < 15 % of radius and arc ≥ 30°, else `pca`).
- **Filters:** zero-phase Butterworth: 0.5 to 10 Hz (keeps beat shape, used for JVP in a
  24 GHz study), 0.7 to 3 Hz (heartbeat), 0.1 to 0.5 Hz breathing. Literature basis in
  `docs/papers/RADAR/md/` (P5 uses 0.5 to 10 Hz; P13 uses arctangent and 0.7 to 3 Hz). The
  match of P5 and P13 to reference numbers [10] and [11] is **assumed, not checked**.
- **Evaluation:** synthetic recordings with known displacement (JVP-like beat with a, c, v
  waves and x, y descents; breathing; 24 GHz wavelength 12.5 mm; DC offset; 1 mV noise;
  12-bit quantization), 6 ranked scenarios × 5 seeds × 60 s, scored in 10 s windows by
  absolute correlation with the truth through the same filter. Selection rule fixed before
  running.
- **Results:** `hybrid` overall median 0.92; `pca` 0.76; `single` 0.69; arctangent with a
  fitted circle 0.56; DACM 0.17; arctangent around the mean 0.11. Linear methods fail on large
  chest motion (0.10); circle fits fail on small neck motion. A guard sweep over arc sizes
  17° to 202° kept `hybrid` within 0.01 of the better of `pca` and arctangent. Weak signal
  (8 mV arc radius) is a hardware limit: best 0.42, 0.88 if the firmware averaged 16 reads
  (what-if, not done). Wide band beat narrow in 5 of 6 scenarios.
- **Fidelity:** JS filters match scipy within 3e-9; 8 method-window scores re-derived
  with numpy/scipy matched to 4 decimals.
- **Real RABITS capture** (`data/rabits_Sep_15_1519.csv`): line-like I/Q cloud on a coarse
  ADC grid; `hybrid` correctly falls back to `pca` on every window. Cannot rank methods (no
  ground truth).

### 3.5 Website (`receiver/`, served at `/capture/`)

- Pages: **Sessions** (`sessions.html`), **Capture** (`index.html`), **Review**
  (`review.html`), one top bar written into the HTML and enhanced by `src/nav.js`.
- Capture flow: Connect, then ask `BOARD?`, then ask the server for that board's session
  (`POST /api/board/session`); the preview runs always, uploading only while recording
  (`src/hub.js` fans the serial lines out). Status line: recording, saving, saved, or not
  saved with the reason.
- Uploads: IndexedDB outbox first, then the server; a chunk is deleted only after 200/201.
- Stale cache: server sends `Cache-Control: no-cache`; `guard.js` repairs a page whose
  script fails to load (at most twice per tab).

### 3.6 Verification methods

- TDD for all code. Suites: `pytest` (server plus firmware host tests via g++),
  `node --test` (website), `arduino-cli compile`.
- Browser checks: headless Chrome driven over the DevTools protocol from small Node
  scripts, on scratch databases and ports (8765 to 8768), never the owner's database. The
  scripts lived in the session scratchpad and are gone; the pattern: start
  `google-chrome --headless=new --remote-debugging-port=<p>`, open a tab via
  `/json/new`, drive with `Runtime.evaluate`, screenshot with `Page.captureScreenshot`.
  Web Serial cannot be picked headless: stub `navigator.serial` to check that Connect
  opens the picker.
- Bugs were reproduced before fixing (stale module served through `Fetch.fulfillRequest`;
  old files cached by a legacy server on the same port).
- Hardware: raw `termios` read of `/dev/ttyACM0` (no pyserial in the venvs), printing the
  board ID and never the key.

## 9. Gotchas

- `FHIR_ADMIN_PASSWORD` is read only by `seed`. To change a password later:
  `source .env/prata.env && .venv/bin/python -m fhir_server set-password --username admin`.
- `.env` is a folder; secrets live in `.env/prata.env`, sourced in every server terminal.
- After changing Python code, restart the server; page files need only a reload. A page
  showing *Updating outdated files…* repairs itself; *This page failed to load* means use
  Ctrl+Shift+R.
- Login curl needs `-H 'Content-Type: application/json'`.
- Only one program can hold `/dev/ttyACM0`; close Chrome's Capture tab before flashing or
  reading from a terminal. `fuser /dev/ttyACM0` shows the holder.
- End a session only after the Capture page shows **✓ Saved**; chunks of an ended session
  cannot upload.
- Do not print the board key, tokens or passwords in tool output or chat.
- The server process started in this session (port 8000) may not survive it; start it
  again per the run guide.
- Doctors cannot see a patient until they take part in a visit; admins open the first one.
