# Validity review — SATUSEHAT playbook vs FHIR R4

Reviewed: 2026-09-11. Playbook version 7.23. FHIR R4 (4.0.1) from hl7.org/fhir/R4.

How to read: every row in a `satusehat-*.md` "Required / constrained elements" table, every identifier-system URI, and every server-enforceable rule of the cross-cutting files is one claim below. Verdicts: `confirmed` (base R4 says the same), `satusehat-specific constraint` (tighter than base R4 but a valid profile restriction per fhir-profiling.md §5.1.0.8), `conflict` (base R4 forbids it: element/type absent from R4, cardinality/type mismatch, code-system URI defined differently, or a protocol-level R4 SHALL violation such as a mandated media type), `unverifiable` (the captured R4 pages do not cover it). Internal SATUSEHAT disagreements are systemic issues, not conflicts. Claim numbering is continuous across this file and [VALIDITY-REVIEW-claims.md](VALIDITY-REVIEW-claims.md), which holds the Practitioner, Organization/Location, Condition, Procedure, RelatedPerson, data-type, REST/validation, terminology, use-case and overview rows.

## Systemic issues
| # | Issue | Impact on our server |
|---|---|---|
| S1 | `build.fhir.org` is the R6 CI build; SATUSEHAT is R4. Only two orientation pages were captured from it. | Never cite fhir-ci files for element rules. |
| S2 | SATUSEHAT has no `Device` resource page (`fhir/resources/device/` → redirect notice); Device is absent from its resource list. | Device/DeviceMetric profiles must be defined by us from base R4 — no national profile to conform to. |
| S3 | FETCH-LOG: no other source failed, but `term-loinc-laboratory` is reported `changed` on every `check.py` run because of Cloudflare per-request email obfuscation. | Treat that id as a false positive; any other `changed` id is a real upstream edit that may invalidate rows below. |
| S4 | Earliest allowed date: `res-observation`/`res-patient`/`res-encounter`/`res-condition`/`res-procedure`/`interop-rme-rawat-jalan` say not before 03 June 2014; `api-list-response` (RuleNumber 10132) says "Past Date older than 31st August 2022" is not allowed. | Pick one lower bound (recommend 2014-06-03, the profile-page value) and document it; make it configurable. |
| S5 | Patient IHS identifier system: `res-patient` profile text says `https://fhir.kemkes.go.id/id/patient-ihs-number`; every API/MPI example uses `https://fhir.kemkes.go.id/id/ihs-number`. | Store `ihs-number`; accept `patient-ihs-number` as a search alias. |

| S13 | Single-valued references are printed inside JSON arrays on the profile pages: `Observation.encounter`; `Encounter.class`/`subject`/`serviceProvider`; `Condition.subject`/`encounter`/`recorder`; `Procedure.subject`/`encounter`/`onBehalfOf`/`location`. `Encounter.location[i]` is printed as a bare `{reference, display}` object. | Never copy the example JSON shapes; validate against R4 cardinality (a JSON array on a 0..1 element is a structure error). |

## Consequences for sub-project 2 (the server)
Conflicts (one bullet each):
- POST/PUT bodies: accept both `application/fhir+json` (R4 SHALL) and `application/json` (SATUSEHAT) on request bodies; always emit `application/fhir+json`.
- PATCH: accept `Content-Type: application/json-patch+json` as R4 requires **and** `application/json` for SATUSEHAT-style clients when the body parses as a JSON Patch array; emit `415` only when neither applies.
- Blood pressure: store device BP as one R4 Vital Signs Observation (`code` 85354-9, components 8480-6 + 8462-4) and derive the two standalone SATUSEHAT Observations (8480-6, 8462-4) on export; accept both shapes on input.
- `Encounter.location`: validate as a BackboneElement (`location[i].location` Reference 1..1); reject the playbook's bare-Reference shape with a structure error.
- `Condition.verificationStatus`: bind to `http://terminology.hl7.org/CodeSystem/condition-ver-status` (con-3/con-5); reject or map the `https://www.hl7.org/fhir/Codesystem-...` web-page form.
- `SampledData.origin/period/dimensions` and `Signature.when/who` are scalars (1..1); reject array forms.
- `CodeableReference` and `RatioRange` do not exist in R4; do not implement them (no R4 element uses them).
- `BillingStatus` and `ChargeItemResponse` are not R4 resource types; the CapabilityStatement and router only expose R4 names (see also S20).

Systemic issues:
- S1, S3, S9: no server consequence (citation hygiene, scrape-check noise, out-of-scope pharmacy).
- S2/S20: define Device and DeviceMetric profiles from base R4 (fhir-profiling.md checklist); the CapabilityStatement lists R4 names only.
- S4: one configurable earliest-date bound (default 2014-06-03); S22: reuse the nine printed RuleNumbers, allocate our own beyond them.
- S5/S6/S7: canonical identifier systems `https://fhir.kemkes.go.id/id/{nik,nik-ibu,ihs-number,paspor,kk}` and `http://sys-ids.kemkes.go.id/<resource>/<org-id>`; accept the documented variants (`patient-ihs-number`, `/organization/` prefix, trailing slash) with a warning.
- S8: `Observation.performer` required only in the visit profile, optional in the device-feed profile.
- S10/S11/S27: consciousness = LOINC question + SNOMED answer; SpO2 = local choice documented as R4 `2708-6` `%`; category always `observation-category`.
- S12: NIK patients need identifier+name+birthDate+gender+address(+administrativeCode); newborns additionally `multipleBirthInteger`; `multipleBirth[x]` otherwise optional.
- S13/S15/S16/S19/S23: validator follows R4 tables (single-valued elements, JSON booleans, `in-progress`, `id` not uuid); never seed from playbook examples.
- S14: `Coding.system` must be a CodeSystem canonical (`terminology.hl7.org`), never an hl7.org page URL.
- S17/S18/S21/S25: author StructureDefinitions with explicit `min`/`max`, `fhirVersion 4.0.1`, and our own extension definitions for administrativeCode/birthPlace/citizenshipStatus/serviceClass.
- S24: bind `Procedure.usedCode` extensibly (FHIRDeviceTypes + KFA); bind `Observation.component.code` to LOINC.
- S26/S28: mint our own Practitioner/Organization ids; region codes as strings.

SATUSEHAT-specific constraints that change server validation (grouped):
- Required-element tightening (min 1): Observation `subject`, `encounter`, `code.coding`; Patient `identifier`, `name` (+ MPI set); Encounter `identifier`, `subject`, `period`, `location`, `serviceProvider`, `diagnosis.use/rank`, `reasonCode.coding`, three `statusHistory` entries with `start`+`end`; Condition `code`, `encounter`; Procedure `code.coding`, `encounter`; Practitioner `qualification.code.coding`; Organization `partOf` (sub-orgs), `contact.purpose.coding`; Location `extension.serviceClass`; RelatedPerson `communication.language.coding`.
- Reference-target narrowing: `subject` → Patient only; `participant.individual`, `performer`, `recorder` → Practitioner; reference targets must exist (RuleNumber 10124).
- Terminology mandates: `Condition.code` ICD-10 (one coding per Condition) or kemkes `clinical-term`; `Procedure.code` ICD-9-CM; Observation `code` LOINC + UCUM quantities; `gender` limited to `male|female`; kemkes systems admitted under Extensible/Example bindings (interpretation, category, dischargeDisposition, usedCode); unknown codes rejected with RuleNumber 10001/10002.
- Identifier systems: fixed URIs per resource (RuleNumber 10117); Patient uniqueness per NIK; `id` = IHS number for Patient.
- Date/time policy: `+00:00` offset, full `YYYY-MM-DDThh:mm:ss+00:00` on validated dateTimes, no future dates (except period-type elements), lower bound per S4; `birthDate` full precision.
- REST surface: Bearer token on every call; JSON Patch limited to `op: replace`; no PUT on Patient; custom Patient search `nik` and Practitioner `birthdate`; `5xx` as `text/plain`; server-side duplicate-Encounter rejection; `Content-Type` ignored on GET.
- Posting order: Organization/Location/Practitioner → Patient → Encounter (`arrived|in-progress`, class `AMB`) → clinical resources → Encounter PUT to `finished` with diagnoses (chief complaint `CC` + ICD-10) and `period.end`.
- `Address`: keep `district`/`state` with R4 meaning and carry kelurahan/RT/RW in the `administrativeCode` extension; do not require `Address.type`.
- Extensions to implement: `administrativeCode`, `birthPlace`, `citizenshipStatus` (Patient); `serviceClass`/`upgradeClassIndicator` (Encounter.location, Location); `meta.profile` canonicals `https://fhir.kemkes.go.id/r4/StructureDefinition/<Resource>`.
