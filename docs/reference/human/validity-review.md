# Validity review — SATUSEHAT playbook vs FHIR R4

Source: `docs/reference/claude/VALIDITY-REVIEW.md` and `docs/reference/claude/VALIDITY-REVIEW-claims.md` (reviewed 2026-09-11, playbook version 7.23, against FHIR R4 4.0.1 from hl7.org/fhir/R4).

## What was checked, and how

Every "required / constrained elements" row in each `satusehat-*.md` file, every identifier-system URI, and every server-enforceable rule from the cross-cutting SATUSEHAT files was treated as one claim and checked against the matching FHIR R4 source page. Each claim was given one of four verdicts: **confirmed** (base R4 already says the same thing), **satusehat-specific constraint** (SATUSEHAT is tighter than base R4, but in a way FHIR's own profiling rules explicitly allow — narrower cardinality, a narrower value set, a narrower reference target), **conflict** (base R4 actively forbids or contradicts what SATUSEHAT states — a missing element, a mismatched type or cardinality, a code-system URI defined differently, or a protocol-level rule SATUSEHAT breaks), or **unverifiable** (the FHIR R4 pages captured in this compilation simply don't cover the topic, usually because it's a purely national/administrative rule with no FHIR counterpart). Disagreements *within* the SATUSEHAT playbook itself — one page contradicting another — were tracked separately as systemic issues rather than being counted as conflicts, since they say nothing about R4 compatibility on their own.

In total, 310 claims were checked (122 in the entry file, 188 in the continuation file): **172 confirmed**, **108 satusehat-specific constraints**, **9 conflicts**, and **21 unverifiable**. That ratio is itself informative for the project: the overwhelming majority of what SATUSEHAT asks for is either identical to base R4 or a legitimate profile-style tightening of it — genuine incompatibilities with the standard are rare, concentrated, and (as the conflict list below shows) mostly small, mechanical mismatches rather than deep architectural disagreements.

## Systemic issues, grouped by theme

**Non-normative or noisy sources.** The FHIR CI-build pages used for orientation (S1) describe a future draft release (R6), not R4, and must never be cited for a rule, verb, or cardinality — only the `fhir-r4/*`-sourced files are authoritative for that. Separately, one page (`term-loinc-laboratory`, S3) used to report as "changed" on every freshness check purely because of a Cloudflare email-obfuscation artifact (a per-request random hex fragment in an obfuscated `mailto` link); this was resolved on 2026-09-12 by normalising that hex fragment out of the converted Markdown before hashing (`tools/scrape/convert.py`), and the page has been re-fetched — `check.py` now reports it `unchanged` like every other source. Any page reported `changed` by `check.py` going forward is a real signal that the rows built from it may need re-checking.

**Identifier-system inconsistencies.** Several SATUSEHAT identifier systems are stated two different ways on different pages: the Patient IHS number appears as both `.../id/patient-ihs-number` (profile prose) and `.../id/ihs-number` (every actual API/MPI example) (S5); local resource-identifier namespaces appear with different placeholder syntax and stray trailing slashes across profile pages and the use-case page (S6); the Observation identifier system is given one way in prose and another in the worked JSON example on the same page (S7); and Practitioner IHS numbers appear in two different digit-count formats with no identifier-system URI ever stated for them at all (S26). The consistent fix across all four is the same: pick one canonical form per resource, and accept the documented variants as aliases on input rather than trusting any single page's spelling.

**Undocumented or disagreeing mandatory-element sets.** No SATUSEHAT profile page states a numeric cardinality anywhere — only an asterisk marking an element "wajib" (mandatory), and even then, whether an *unstarred* element is mandatory is said to depend on which Panduan Interoperabilitas (use-case guide) applies (S17). This shows up concretely for Observation, where `performer` is required on the outpatient-visit use-case page but not on the Observation profile page itself (S8), and for Patient, where the profile page's mandatory set (`identifier`, `name`, `multipleBirth[x]`) disagrees with the MPI page's mandatory set (`identifier`, `name`, `birthDate`, `gender`, `address`, `address-extension`, no `multipleBirth[x]`) (S12). The same kind of page-against-page disagreement affects even something as basic as the earliest date a resource may carry: the Observation/Patient/Encounter/Condition/Procedure profile pages and the outpatient use-case page all say no date should be earlier than 03 June 2014, while the API error-code page's RuleNumber 10132 separately says a "Past Date older than 31 August 2022" is rejected — the playbook simply states two different lower bounds and does not say which one governs (S4). Our server has no choice but to write these cardinalities and bounds down explicitly and by hand, rather than inferring them from any single playbook page.

**Terminology and vocabulary mismatches.** Several vital-sign and coding choices disagree across playbook pages: level-of-consciousness is coded one way in an appendix table and a different way (LOINC question plus SNOMED answer) on the use-case page, with even the display strings differing between the two (S10); no SpO2 LOINC code appears anywhere in the playbook, and systolic/diastolic blood pressure are documented as two separate Observations rather than as components of one panel, which is a valid base-R4 shape but not what R4's own Vital Signs profile recommends (S11); `Coding.system` values are sometimes printed as human-readable hl7.org web page URLs rather than the actual CodeSystem canonical URIs used elsewhere in the same corpus (S14); device-related codes mix a FHIRDeviceTypes binding in prose with a KFA (national drug/device dictionary) code in the worked example, and Observation components have no documented code system at all (S24); a pregnancy-status Observation's category system and a data-type label both look like straightforward typos (S27); and the terminology corpus captured for this compilation contains no vital-sign LOINC codes at all — the table in file 13 was sourced from the use-case page, not the terminology pages, and one referenced external terminology catalogue carries a future publication date (S29).

**Copy-paste and transcription defects in the playbook text itself.** A long tail of scrape-and-source errors were found and are worth treating as noise rather than rules: single-valued references printed as JSON arrays in worked examples (S13); quoted-string booleans, swapped coordinates, mismatched IHS-number digit counts between an example's prose and its JSON, and other JSON defects across multiple resource examples (S15); typos in code values and element names such as `In-progress` for the code `in-progress`, `Practicioner`, and `valueBooelean` (S16); API-template artefacts like a `Content-Type` header marked mandatory on a bodyless GET, and resource ids described as UUIDs when the actual ids shown are IHS numbers (S19); and a cluster of copy-paste errors that change the actual meaning of a sentence — a PractitionerRole search parameter description that describes a different resource entirely, a RelatedPerson page whose opening paragraph names the wrong resource, and similar (S23). None of these should ever be copied into our validator or seed data; every one is resolved by preferring the matching R4 element table over playbook prose.

**Resource-list and version-declaration gaps.** SATUSEHAT's own list of "46 resources used for interoperability" includes two names — `BillingStatus` and `ChargeItemResponse` — that are not real FHIR resource types at all, and separately omits several resources (`PractitionerRole`, `Bundle`, `OperationOutcome`, `Device`) that other SATUSEHAT pages clearly use (S2, S20). PractitionerRole has this same profile-page gap as Device: SATUSEHAT publishes an API page for it (`api-catalogue/integrations/apis/practitioner-role/`) but no profile page — `fhir/resources/practitioner-role/` was probed on 2026-09-12 and, like the Device URL, returns a "Redirect Notice" page. No SATUSEHAT page states its FHIR version in prose anywhere; the R4 conclusion this whole compilation relies on is inferred entirely from the API base path and profile canonical URLs (S21). Our server's `CapabilityStatement` and internal resource router must be driven by real R4 resource names and an explicitly declared `fhirVersion`, independent of what SATUSEHAT's own resource list says.

**Everything else.** A handful of smaller, self-contained issues round out the list, including one outright internal contradiction the playbook never resolves: the Rawat Jalan use-case changelog for v6.2 states that posting a separate `Medication` resource "sudah tidak bisa digunakan" (can no longer be used), yet steps 16 and 18 of that same use-case page still list "2 kali POST" (two POST calls, one of them the separate Medication POST) as an available option — the changelog and the step-by-step instructions on the same page disagree with each other and neither is marked as superseding the other (S9). This is out of scope for our device-monitoring server (no pharmacy/medication workflow is planned), so it is recorded here as a contradiction rather than something the server needs to pick a side on. Beyond that: the validation error-code dictionary reuses one rule number for two different error conditions and only documents nine numbers total, so our own server needs distinct numbers for anything beyond those nine (S22); extension definitions referenced by URL (`administrativeCode`, `birthPlace`, `citizenshipStatus`, `serviceClass`, and others) have no printed structure anywhere in the captured corpus, only worked examples, so we must author these ourselves (S18); the SATUSEHAT data-type reference pages contain their own transcription errors and even list two R5-only types (`CodeableReference`, `RatioRange`) as if they were part of R4 (S25); and the national facility/region master-data API (MSI) has internal inconsistencies of its own — inconsistent status enumerations, a numeric field returned as a string, and no master region-code API page at all — none of which has any FHIR R4 counterpart to check against (S28).

## The nine conflicts, one at a time

**PATCH request media type.** SATUSEHAT's API pages describe every PATCH call as sending a JSON Patch array with `Content-Type: application/json`. FHIR R4 states that a JSON Patch body SHALL be sent with `Content-Type: application/json-patch+json` specifically — a generic `application/json` header is not what the standard permits for a patch body. Our server should accept `application/json-patch+json` as R4 requires, and additionally tolerate `application/json` when the body parses as a valid JSON Patch array (to stay compatible with SATUSEHAT-style clients), rejecting only requests that match neither.

**Write-request media type generally.** The same media-type gap recurs for ordinary POST/PUT bodies: SATUSEHAT's pages describe write calls sending `Content-Type: application/json`, while FHIR R4 states that `application/fhir+json` SHALL be used by clients and servers for FHIR content, with the bare `application/json` tolerance applying only to the `Accept` header, not to what a client actually sends. Our server should accept both `application/fhir+json` and `application/json` on incoming request bodies, but should always emit `application/fhir+json` itself.

**`Encounter.location` shape.** SATUSEHAT's Encounter profile page marks `location[i]` mandatory and describes it as having "tipe data Reference," with its worked example printing a bare array of `{reference, display}` objects. In FHIR R4, `Encounter.location` is not itself a Reference — it is a BackboneElement, and the actual `Reference(Location)` lives one level down, at `location.location`, which is the element that is 1..1. Our server should validate incoming Encounter data against the correct nested BackboneElement shape and reject the playbook's flattened example shape as a structural error, even though raising the *cardinality* of `location` to mandatory would otherwise have been a perfectly ordinary profile constraint.

**`Condition.verificationStatus` code-system URI.** SATUSEHAT's example for `Condition.verificationStatus` prints the system as `https://www.hl7.org/fhir/Codesystem-condition-ver-status` — a human-readable web page URL. FHIR R4 defines the actual CodeSystem canonical for this binding as `http://terminology.hl7.org/CodeSystem/condition-ver-status`. Our server should bind to the correct `terminology.hl7.org` URI and either reject or transparently map the web-page-style URI on input, since accepting it as a distinct code system would silently break the con-3/con-5 invariants that depend on recognising specific codes from that system.

**`CodeableReference` as a supposed R4 data type.** SATUSEHAT's own data-type reference pages list `CodeableReference` (a concept-plus-reference type) as if it were part of FHIR R4. No FHIR R4 page in the captured corpus defines any such type — it does not exist in R4 at all and was introduced only in a later release (R5). Our server must never implement or accept `CodeableReference` anywhere; any playbook example that uses it should be treated as describing a future FHIR version, not R4.

**`RatioRange` as a supposed R4 data type.** The same data-type pages also list `RatioRange` (with `lowNumerator`/`highNumerator`/`denominator` sub-elements) as an R4 type. Like `CodeableReference`, this type does not exist anywhere in FHIR R4 — it too is an R5 addition. Our server should treat it the same way: never implement it, and treat any playbook reference to it as out of scope for an R4-based server.

**`SampledData` sub-elements printed as arrays.** SATUSEHAT's data-type pages show `SampledData.origin`, `.period`, and `.dimensions` each wrapped in JSON array brackets. FHIR R4 defines all three as scalar, single-valued elements (`origin` 1..1 SimpleQuantity, `period` 1..1 decimal, `dimensions` 1..1 positiveInt) — a JSON array is not a valid representation of a 1..1 element at all under R4's serialization rules. Our server's parser should reject an array in any of these three positions as a structural error rather than accepting it as a list of one.

**`Signature.when`/`Signature.who` printed as arrays.** The same class of error recurs for the `Signature` type: SATUSEHAT's pages print `when` and `who` inside array brackets, while R4 defines both as scalar 1..1 elements (`when` instant, `who` Reference). The fix is identical to the `SampledData` case — reject the array form as invalid.

**Non-existent resource names in the supported-resource list.** SATUSEHAT's own list of resources it says are used for interoperability includes `BillingStatus` and `ChargeItemResponse`. Neither name corresponds to any actual FHIR R4 resource type anywhere in the captured corpus, including the FHIR workflow page's own exhaustive request/event resource lists. Our server's `CapabilityStatement` and internal router must be built entirely from real R4 resource type names; SATUSEHAT's list should be treated as advisory background, never as the authoritative resource catalogue.

## What this means for building the server

Overwhelmingly, SATUSEHAT is a legitimate FHIR R4 profile set: the majority of its claims are either identical to base R4 or are exactly the kind of narrowing — tighter cardinality, narrower reference targets, restricted terminology bindings — that FHIR's own profiling mechanism (see `14-fhir-profiling-a-new-device.md`) explicitly permits. That means most of this review's findings translate directly into StructureDefinition constraints: mandatory-element sets for Observation, Patient, Encounter, Condition, and Procedure that raise several base-R4 optional elements to 1..1; reference-target narrowing (a `subject` that must be a Patient, not any allowed target); and terminology bindings that admit Indonesian national code systems (ICD-10, ICD-9-CM, LOINC, KFA, and kemkes-specific systems) under R4's extensible and example binding strengths.

The nine genuine conflicts are the parts of the playbook our server must *not* copy literally: two media-type mismatches (write and patch bodies), one structural mismatch (`Encounter.location`), one wrong code-system URI, two data types that don't exist in R4 at all, two data-type serialization errors (arrays where R4 wants scalars), and two resource names that aren't real R4 types. In every one of these nine cases, the resolution is the same shape — accept both forms where SATUSEHAT-style clients might reasonably send the wrong one, but always validate against and emit the real R4 rule, and never let a SATUSEHAT worked example be trusted over the matching R4 element table.

The systemic issues, in turn, are less about R4 compatibility and more a warning about the playbook as a source: it contains real internal disagreements between its own pages (mandatory-element sets, identifier-system spellings, terminology choices) and a long tail of transcription defects (typos, swapped coordinates, quoted booleans, mismatched digit counts) that must never be copied into a validator or seed data set. Wherever this compilation's own `claude/*.md` files had to make a judgment call between two disagreeing SATUSEHAT pages, that call — and the reasoning behind it — is recorded in the corresponding file, and this review is the map of every place such a call had to be made.
