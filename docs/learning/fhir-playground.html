FHIR Pipeline Playground

One vital-sign reading from the radar device, followed from JSON on the wire to the doctor's screen. Edit the body on the left, press POST, and watch each stage of a SATUSEHAT-style FHIR R4 server accept or reject it. Every check names the reference file it comes from.

Sensor → value
Observation
The radar gives you HR = 72. FHIR needs to know what 72 is, who it belongs to, when, and in which unit.
Encoding (ADC)
JSON
The value is serialised as text. A quoted "72" is a string, not a number — the same class of bug as a wrong ADC word length.
Frame + header
HTTP request
Method, address, headers = the frame header. Body = payload. Content-Type is the "what encoding" flag.
Checksum / range check
Validation
Structure (R4 base rules), then profile (SATUSEHAT tightenings), then references (does that patient exist?).
Memory / DAQ buffer
Store
Server assigns an id and a version, and answers 201 Created. Nothing is written if any check failed.
Readout
Search → Bundle
The doctor asks a question in the URL; the server answers with a Bundle. The patient sees the same data rendered plainly.

Rulings this playground makes where the sources disagree

  
CLAUDE.md: "Do not silently pick a side." These are the sides picked here, and why. They are proposals for the real server, not decisions.

  

    
TopicSource ASource BPlayground does

    
Request media typeSATUSEHAT: Content-Type: application/json (satusehat-rest-api-and-validation.md)R4: clients and servers SHALL use application/fhir+json; 415 when unsupported (fhir-rest-api.md)Accept both; emit application/fhir+json. VALIDITY-REVIEW.md consequence list.

    
Blood pressure shapeSATUSEHAT Rawat Jalan: two standalone Observations, 8480-6 and 8462-4 (S11)R4 Vital Signs: one 85354-9 panel with both as component (fhir-observation.md)Accept both shapes. Store what was sent; a real server would store the panel and derive the pair on export (CLAUDE.md).

    
Earliest allowed dateProfile pages: not before 2014-06-03RuleNumber 10132 text: not older than 2022-08-312014-06-03, the profile-page value (S4 recommendation).

    
Time zoneSATUSEHAT: send UTC+00, e.g. …T10:35:00+00:00R4: any offset is valid; a zone is required when a time is presentRequire a zone (error); non-zero offset is a warning, not a rejection. Stored value would be normalised to UTC.

    
SpO₂ codeSATUSEHAT corpus: no SpO₂ LOINC at all (S11, S29)R4 Vital Signs: 2708-6, unit %Use 2708-6 / % and say so in the profile.

    
Observation.performerRawat Jalan use case: wajibObservation profile page: not starred; R4 0..*Optional for device-sourced readings (S8). Not checked here.

    
Device profileSATUSEHAT: no Device page at all (S2)R4 Device / DeviceMetric existSeeded Device is plain R4. Its profile is a later sub-project goal.
